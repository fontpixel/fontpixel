### On Third-Party Trademarks in Font Names

This site's inclusion decisions are **based solely on copyright licensing**. Some font names contain third-party registered trademarks:

- **Nominative use (kept under their original names, not renamed)**: `ibm-bios` / `ibm-cga` / `ibm-cga-light` /
  `ibm-ega` / `ibm-mda` / `ibm-vga` (IBM® belongs to IBM Corp.; these are VileR's re-creations, and the names identify
  which hardware ROM the glyphs come from — there is no other honest way to name them); `adobe-helvetica` / `adobe-times` /
  `adobe-courier` / `adobe-new-century-schoolbook` / `adobe-symbol`
  (Helvetica® etc. belong to Monotype); `gnu-unifont` (Unifont itself is an official GNU software package,
  an authorized use).
- **Borderline coinages (very low risk, noted for reference)**: `bitbuntu` (alluding to Ubuntu®, Canonical),
  `monocraft` (alluding to Minecraft®, Mojang/Microsoft), `yarndings-12` / `yarndings-20`
  (alluding to Wingdings®, Microsoft; but published by Google Fonts, which has already cleared it with their legal team),
  `5thelement` (a 1997 movie title, weak protection and an unrelated product category).
- The "DOS" in `dos-gothic` / `dos-myungjo` / `dos-pilgi` / `dos-iyagi-boldface` / `dos-saemmul`
  is a generic term (Microsoft's trademark is MS-DOS), and is not covered by this concern.

Conclusion: **none of them are renamed**. Renaming would neither remove the trademark strings inside the font files' XLFD/FAMILY_NAME
nor avoid making the catalog lose its identifying value. This position is stated in the disclaimer section of the site's "About" page: inclusion under the original name does not imply
endorsement by or affiliation with the trademark holder.

### Pre-existing Issues Fixed Along the Way

- **Importer pattern ambiguity (10 families)**: `take`/`convert_take`/`license_files` originally only matched by
  filename glob and recursed the entire directory tree; when upstream placed same-named files in different subdirectories, all of them would match, with the later one silently
  overwriting the earlier one, causing every rerun to rewrite files and making which copy actually got included dependent on sort order. Path
  patterns with `/` are now supported (root-directory files anchored with `./NAME`), and an error is raised on a same-name collision. The affected
  zlabs series, wqy-unibit, hicchicc series, tiny5, and monocraft have each been pinned to **the copy that is currently actually in effect**,
  with zero change in output. After the fix, a full import gives `imported=0`, fully idempotent.
- **boutique-bitmap-7x7 / 9x9**: these two slugs were previously manually merged into `boutique-bitmap`
  and removed, but the `[[family]]` entries were still present in the manifest, so a full rerun would recreate them. They have now been changed to
  `[[todo]]` entries with the reason documented.
- **Fonts that self-report a single-byte charset but are actually Unicode-encoded (4 families, recovered 1437 glyphs)**:
  `lemon.bdf` declares `CHARSET_REGISTRY "ISO8859"`, but its actual ENCODING goes up to 65379;
  the pipeline decoded it according to the self-reported single-byte charset, discarding all glyphs with code points >0xFF as "cannot be mapped to
  Unicode" — leaving only 191 of 1030 glyphs. The same situation affects bitocra (dropped 335),
  bitbuntu (whose registry is even misspelled as `iSO8859`, dropped 253), and envypn (dropped 10).
  The code-point ceiling of a single-byte charset is 0xFF; any larger value appearing can only mean the font has the registry field wrong,
  and the only reasonable explanation is that it is in fact Unicode-encoded. `decode_cp` now special-cases
  the single-byte registries iso8859/koi8/ascii/iso646: code points >0xFF are passed through as-is as
  Unicode with a note, rather than being discarded.
- **Not yet addressed**: 3897 glyphs are still discarded under traditional double-byte CJK encodings
  (ksx1001.1997 in the baekmuk series, GB2312.1980 in isas-song,
  jisx0208.1990 in pixel-mplus and tekuplus). These are code points that are simply unassigned or fall within
  user-defined ranges in their respective encodings — a different nature from the "registry written wrong" case above, so the same fix cannot be applied;
  each encoding needs to be individually verified, left as a separate task.
- **Removed the `commercial` field (2026-08-31)**: this field recorded, per font, "whether it can be used commercially", but this site's inclusion
  standard already requires the license to explicitly allow commercial use, so it is impossible for a font on the site to be non-commercial-use —
  the field was always true, making it redundant. Worse, it was unreliable: `licenses.py`'s `COMMERCIAL_OK` whitelist did not cover bare GPL or
  `LicenseRef-Baekmuk`, causing 9 auto-detected families (wqy-bitmap-song / wqy-unibit /
  unifont-ex / uranus-pixel / nightgazer-bitmap / the four baekmuk families) to fall through to `null` "unknown",
  self-contradicting the site's claim that "every single one can be used commercially with confidence" — when in fact all of these licenses do permit commercial use.
  It has now been removed altogether from `LicenseInfo`, the build artifacts, `family.toml` (96 files), the manifest, the site's zod contract,
  and the five-language i18n (`commercialOk` was a dead entry left over from removing the commercial-use filter).
- The `family.toml` template generated by the importer previously had only Chinese-language fields, missing `name_en` / `authors_en` /
  `description*` / `aliases` / `confidence` / `[merge]` / `[variants]`, inconsistent with the format of the 125
  `family.toml` files already in the repository, requiring manual backfilling one by one. The template has now been completed, and the manifest is now the
  single source of truth for these fields.

## 2026-09-01 Removal: mplus_hzk_12 (public-domain dedication does not cover the glyphs)

`mplus_hzk_12` (Luckeee, 12px, one variant) was included on 2026-08-21 on the strength of the Unlicense
file bundled with its repository. That dedication turns out not to cover the part of the font that matters.

The repository's own README describes the font as M+ supplying Latin and Japanese with HZK12 supplying the

the existing Chinese bitmap fonts had no clear licence.

The affected glyphs are not incidental. The font covers GB/T 2312 in full (6763 of 6763) out of 10609
glyphs, so its entire Chinese repertoire rests on that assumption. This fails the collection's requirement
that a licence verifiably cover the exact files catalogued here. The family, its build data and its

unclear provenance.
